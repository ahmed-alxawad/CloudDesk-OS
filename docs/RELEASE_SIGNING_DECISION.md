# Release Signing Decision Record (Phase 17B, Part 17)

No signing key is generated by this document or by this pass. This is a
comparison of the two realistic options already identified in
`docs/RELEASE_INTEGRITY.md`, prepared so an eventual publication decision
does not have to research this from scratch.

## Option A — GitHub Artifact Attestations (Sigstore-backed, keyless)

| Property | Detail |
| --- | --- |
| Trust root | Sigstore's public transparency log (Rekor) + GitHub's OIDC identity for the specific Actions workflow run that produced the artifact |
| What the user verifies | That the artifact was produced by a specific, named GitHub Actions workflow in this specific repository, at a specific commit — not an arbitrary claim from whoever uploaded a file |
| Automation requirement | Must build and attest inside GitHub Actions (or another OIDC-compatible CI) — cannot be generated from a local developer machine after the fact in the normal flow |
| Key management | None — no long-lived private key exists anywhere; short-lived signing certificates are issued per-build and tied to the CI identity |
| GitHub dependency | Yes, structurally tied to GitHub Actions + GitHub's own attestation infrastructure |
| Offline verification | No — `gh attestation verify` needs network access to query Rekor/Fulcio at verification time |

## Option B — minisign detached signatures (project-controlled key)

| Property | Detail |
| --- | --- |
| Trust root | A single Ed25519 keypair the project generates and controls; the public key must be published somewhere independent of the artifact download location |
| What the user verifies | That whoever holds the private key signed this exact file — trust reduces entirely to how well that one private key is protected |
| Automation requirement | None required — can be run from any machine with the private key, including a maintainer's own, at release time |
| Key management | Real ongoing responsibility: secure generation, secure storage (ideally offline/hardware-backed), a plan for what happens if it's ever lost or compromised, and how a compromised key gets revoked/rotated |
| GitHub dependency | None — works identically regardless of where the artifact is hosted |
| Offline verification | Yes — `minisign -V` needs only the already-published public key and the downloaded files, no network round-trip |

## Recommendation

**Primary: Option A (GitHub Artifact Attestations)** if and when publication
happens through GitHub Releases, which is the only distribution channel this
project has actually discussed (`GOAL.md` G1's `curl -fsSL <official-
install-url>` contract implies a GitHub-hosted release). It requires no new
key-management burden for a project of this size, and ties every artifact's
provenance to the exact CI run and commit that built it — a stronger, more
specific claim than "someone with the key signed this."

**Complementary, not a replacement: Option B (minisign)** is worth adding
later specifically to give operators an **offline** verification path — a
real operational need for anyone provisioning CloudDesk-OS on an air-gapped
or network-restricted server, where reaching Sigstore's transparency log at
verification time is not guaranteed. This is optional hardening, not a
blocker for an initial release.

**Not implemented in this pass**: neither mechanism is wired up. No private
key exists, no CI workflow attests anything yet. This record exists so the
choice does not have to be re-derived when publication is actually
authorized.
